# Mynx Trees — Canary 5 runtime procedure

Current candidate: `0.1.0+26.2-canary5`, `mynx-trees-private-0.1.0+26.2-canary5.jar`. The canonical manifest records its exact SHA-256 and implementation checkpoint. It is ACTIVE, NOT_DEPLOYED, and RUNTIME_UNTESTED. Build/static checks are not Minecraft observations.

Manual C4 observation (external, not a managed Workbench result): Silver Birch Leaves were still inordinately bright. Changing C4's absent-state fallback to upper-waving foliage did not solve the visual problem. Canary 5 restores absent-state inheritance from corresponding loaded Birch Leaves, retains its leaf-style waving, and applies an intentional `SILVER_BIRCH_VALUE = 0.70F` render compensation; this is not a byte-for-byte reproduction of RU's raw HSB value of `1.0F`.

## Build and static reproduction

Use Java 25, the included Gradle wrapper, and `gradlew.bat clean build` from this project. This runs focused Java and Python regression checks for tree transformation, shader alias policy, exact tint/texture contracts, soil selection and contextual geometry. The assembler locates `originals/assets` in the primary checkout through Git's common directory, validates `build-inputs.json`, and generates resources locally. It requires the exact cached Minecraft 26.2 merged JAR (or `MYNX_MINECRAFT_JAR`). It never changes source references. The standalone `originals/assets/block_wisteria_log_top.png` is the immutable 16x16 user-supplied replacement (SHA-256 `68f630d51c1c900286def61b213b343dcfa5bc166fda85d5c0ade622e87b3d0b`). The pack log top and flat Silver Birch inventory sprite are not packaged. Restricted PNGs, derived JSON and the assembled JAR stay ignored; do not upload the JAR or textures to GitHub or the Sheet. Build inputs record hashes, archive entries, PNG dimensions, licenses, visual-reference behavior, and exact validation tool versions.

## Soil-dependent Silver Birch base bark

**Prerequisite before visual testing:** remove or disable this exact obsolete Matcha Overlays v6 rule from the active overlay pack:

`assets/minecraft/optifine/ctm/mynx/silver_birch_base/silver_birch_base.properties`

It approximates the bottom of a column and conflicts with the new soil predicate. Its companion base PNG is unnecessary after the rule is removed. This mod task has **not** cleaned up any resource pack; perform that separate action only with authorization. No global CTM bypass is used, and unrelated CTM rules should remain.

The special bark applies only to a placed `mynx_trees:silver_birch_log` with `axis=y` and a block immediately beneath it in `mynx_trees:silver_birch_base_soils`. Default members are exactly grass_block, dirt, coarse_dirt, rooted_dirt, podzol and mycelium (all minecraft namespace). The independent block tag is data-pack extensible; it does not change sapling survival or tree generation. Only the four vertical sides change. Both end faces continue using live `minecraft:block/birch_log_top`.

The exact immutable `originals/assets/block_silver_birch_log_base.png` is privately assembled as `assets/mynx_trees/textures/block/silver_birch_log_base.png`, SHA-256 `d0360942c1726406d838c8e48f40a6529bb2eed51751c40e780a5036a269844e`. Ordinary resource-pack overrides of that namespaced texture remain supported. The rendering code chooses one of two baked models from the supplied snapshot; it never writes block state. Geometry keys distinguish branch, delegate geometry and resource-reload model identity. Tag synchronization requests one normal terrain rebuild on the client thread; support changes use vanilla neighboring-section invalidation. These are static design checks, not observed visuals.

Run this matrix first with Fabric and the required dependencies, **without Continuity or Iris**, then with the normal Sodium/Continuity/Complementary stack and the obsolete rule absent. Record each observed result independently.

| Case | Expected result |
| --- | --- |
| Existing natural tree, newly generated tree, sapling-grown tree, player-built upright pillar | Only a log directly on allowed soil has base bark; logs resting on other logs remain ordinary. Existing terrain needs no regeneration or log replacement. |

## Registration, crafting, stripping and fuel

1. Confirm all nine items appear in Natural Blocks and that their display names are correct. Use `/give @s mynx_trees:silver_birch_log 64`, and equivalent commands for `silver_birch_wood`, `silver_birch_leaves`, `silver_birch_sapling`, `wisteria_log`, `wisteria_wood`, `wisteria_leaves`, `wisteria_sapling`, and `sweet_violets`.
2. For both custom log AND wood: one Silver Birch input must craft four vanilla Birch Planks; one Wisteria input must craft four vanilla Pale Oak Planks. No conversion recipe is required. Four matching logs in a 2x2 square must craft three matching all-bark wood blocks. Mixed logs must fail. Check recipe-book unlocks and any installed recipe viewer for duplicate competing outputs.
3. One corresponding leaf block crafts one corresponding sapling. Extra leaves or another species in the grid must not satisfy the one-input recipe.
4. Place log and wood blocks on each axis. Strip each with an axe: Silver Birch maps to vanilla stripped birch log/wood; Wisteria to vanilla stripped pale-oak log/wood. Axis, axe durability, sounds, particles, advancement/event behavior and sneaking/main/offhand behavior should follow the ordinary axe path. Check any installed stripping-toggle integration separately.
5. Confirm custom log/wood can fuel a furnace and smelt into charcoal. Test campfire, soul campfire and smoker direct-log recipes. Plank-family recipes must still take vanilla planks, and unrelated vanilla log crafting must be unchanged. Compare fire spread/burn behavior with birch/cherry counterparts in a contained disposable test area.

## Leaves and saplings

1. In Survival, break each leaf species barehanded and with an ordinary tool, Fortune III tool, shears, and Silk Touch tool. Only shears or Silk Touch yield one corresponding leaf. No sapling or stick may drop. Repeat on natural leaves and across enough blocks to detect accidental probabilistic loot.
2. Grow a tree, remove the entire supporting trunk, and wait for natural leaf decay. It must yield nothing. Check that player-placed persistent leaves remain, that waterlogging works, and that distance values update normally. Strip an intact supporting tree: its leaves must remain supported by vanilla stripped logs/wood and must not decay.
3. Compare composting with vanilla birch/cherry leaves and saplings and Pink Petals: all five custom plant inputs use 30% success. Use repeated trials rather than expecting a fixed per-item outcome.
4. In old-growth birch forest, cherry grove, plains and another non-target biome, grow both saplings by bone meal and normal random ticks in daylight. For normal growth use `/gamerule randomTickSpeed 100` temporarily and restore `3` afterward. Silver Birch always uses the super-birch configuration (height 5 + [0,2] + [0,6]); the distribution includes shorter draws, but never falls back to the ordinary-birch grower. Wisteria always uses the 26.2 cherry trunk/branch/canopy configuration. Nearby flowers should retain the applicable bee-nest variant.
5. Test invalid soil, insufficient light for natural growth, a stone ceiling/column obstructing growth, world-height limits, and adequate clearance after removing the obstruction. Failed growth must leave the sapling and obstruction intact. Do not confuse a sapling advancing to stage 1 or consumed bone meal with successful tree growth.
6. Successful Wisteria growth must produce Sweet Violets around suitable air-above-soil positions, including outside cherry groves, with and without Nemo. Failed growth must not create flowers. Surround test ground with stone, water, occupied flower positions and small builds: decoration must not replace any occupied target, fluid, or unsuitable ground. It is a finite successful-growth pass, not later scanning.

## Fresh terrain and unaffected-biome checks

Use `/locate biome minecraft:old_growth_birch_forest`, `/locate biome minecraft:cherry_grove`, and `/locate biome minecraft:birch_forest`, then teleport safely to fresh terrain. Generate multiple chunks and inspect tree materials and layout; use repeated seeds for a distribution check.

- Old-growth birch: all standing normal/super birches and both fallen-birch branches selected by the original `birch_tall` graph become silver variants. Original height distributions, canopies, bee nests, fallen log lengths/mushrooms, placement filters and 10-or-11 tree-attempt count remain. The selector's conditional probabilities are unchanged (0.00625 fallen super, then 0.5 super, then 0.0125 fallen ordinary, otherwise ordinary). Rare fallen variants require a broad terrain sample; absence in a small sample is inconclusive. `/place feature mynx_trees:silver_fallen_birch_tree` and `/place feature mynx_trees:silver_fallen_super_birch_tree` can isolate their material checks in the disposable world.
- Cherry grove: each existing generation attempt has a 25% Wisteria selection probability and 75% cherry. Do not demand a rigid one-in-four sequence or exact 25% among successfully grown trees; success/clearance can bias that sample. Overall attempt density and placement filters are unchanged. Natural cherries retain their loaded source configuration and bee decorations.
- Ground cover uses the preferred tree-associated design, not the patch fallback. The grove's `flower_cherry` background pass is removed only when its tree population is replaced. Wisteria has one bounded radius-5/48-attempt Sweet Violets decorator; cherry retains Nemo's ordinary decorator when loaded, otherwise one corresponding Pink Petals decorator. Neighboring patches can mix. No second full-density petal population should appear. Exact flower coverage differs from vanilla background patches and needs visual review.
- Ordinary birch forests, other biomes, vanilla birch/cherry saplings and existing tree blocks must remain unchanged. No retrogen exists. The old-growth biome grass tint can visually change existing terrain without replacing any blocks.
- Matcha's inspected biome overrides keep the relevant feature keys; other biome climate, spawning, music and colors must survive except the requested old-growth grass tint. Loaded source tree/fallen-tree materials are copied, leaving shape and unrelated decorators intact. A third-party pack replacing the relevant placed-feature keys is outside this audited graph and is not guessed. An unsupported source feature type fails with an explicit error, not an ordinary-tree fallback.

## Sweet Violets, colors and rendering

1. Place Sweet Violets from all four directions and stack one through four units. Verify orientation, outline, movement/step sound, support loss, exact amount drops, bonemeal increments to four, and a further bonemeal use dropping an extra item. Pink Petals must retain their own identity, names, models and pixels.
2. Inspect ordinary cube leaf geometry, correct saplings and inventory sprites, transparent edges and texture resolution. No bushy, drooping or projecting foliage is shipped. Silver Birch logs use the live `minecraft:block/birch_log_top`; a resource pack changing vanilla birch end grain must change those ends too. All-bark wood has no end-grain face. Wisteria uses the newly supplied standalone log-top image, not the cherry-to-wisteria archive end grain. Inspect both top and bottom; bark on the sides and all-bark wood remain unchanged.
3. Compare Silver Birch Leaves at several X/Z coordinates. They retain the exact positional hue formula `sin(x/10 + sin((z+x)/50)*3)/75 + 0.15` and saturation `0.8F`, but use the intentional rendering-compensation value `0.70F`. They must remain golden outside old-growth birch forest; unrelated leaves must retain their normal colors. Silver Birch Leaves must appear as the normal shaded isometric cube in inventory, hand, recipe viewer and dropped-item rendering, using the leaf block texture with exactly one matching compensated mustard-gold #B3A424 default tint. No flat custom icon or second tint is applied. World leaves retain the same position-dependent variation. Old-growth grass uses #B0C73A with ordinary biome blending across boundaries; #88BB42 is not the custom leaf color.
4. Watch Wisteria leaf particles against ordinary cherry particles: Wisteria uses twelve separately namespaced supplied sprites, with no recolor/replacement of vanilla cherry particle assets. Review with default lighting, then Matcha, Continuity and Complementary. Check transparent leaf edges, culling, distance/fancy graphics, shader foliage classification/wind and biome blending. Wisteria still inherits only its matching vanilla Cherry Leaves assignment when its own state is unmapped. Explicit custom block/tag mappings, even non-waving mappings, always win. No shader material ID is hardcoded in the mod, and no shader/profile file is changed. Soil-dependent Silver Birch base bark is implemented in Canary 3; use the focused matrix above.
5. **Canary 5 Silver Birch visual comparison, using only an authorized dedicated Workbench session:** with Complementary Unbound r5.8.1 + Iris 1.11.2 and foliage waving enabled, compare Silver Birch to the supplied RU reference screenshot under matching sunlight/exposure. PASS requires a substantially darker mustard/golden canopy; sun-facing leaves must no longer be near-white or fluorescent; shaded portions retain useful depth; and positional gold variation remains visible. Silver Birch must visibly wave as leaves under Complementary. Confirm Wisteria remains visually and motionally unchanged beside Cherry Leaves. Repeat with persistent/nonpersistent and waterlogged Silver Birch states, reload shaders, and rejoin; absent states must inherit the loaded corresponding Birch Leaves assignment, explicit Silver Birch mappings must win, and replay must not leave stale results. With Birch Leaves absent from a pack map, no material ID is invented; with Iris absent or shaders disabled, blocks/items must keep ordinary vanilla rendering and no optional-mod class-loading failure. If C5 remains too bright or becomes too dark, record that observation and tune only `SILVER_BIRCH_VALUE` in the next Canary; do not redesign shader classification without new evidence.
6. Repeat natural grove and planted Wisteria tests with Nemo present and absent. Wisteria must have Sweet Violets in both cases and never invoke Nemo's hardcoded Pink Petals decorator. Ordinary cherry must retain Nemo's own behavior when installed, and unrelated flower behavior must remain unchanged. Mynx's own selection and placement uses world-generation randomness; existing Nemo ordinary-cherry/fallen-leaf independent randomness is deliberately not changed.

No Minecraft client, server, GameTest world, runtime profile or testing slot was launched or changed during the implementation. All cases above await observed runtime evidence.
